# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## Unreleased

### Added

- `Config.ReplicaRestoreDelay` (default `1m`). After the primary owner of a partition leaves the cluster, the survivors that hold its backup copies wait this long, counted per partition from the departure, before they re-create the primary copy on the new owner. A member that leaves and comes back within the delay, as in a rolling restart, owns its partitions again by then and receives them from their previous owner, so nothing is restored for it; a member that stays gone has every partition it owned back at `ReplicaCount` copies once the delay has passed, without waiting for a write to touch it. The check runs on the balancer tick, so a millisecond restores on the first tick after the departure; a negative value is rejected by `Validate`. It applies only with `EnableProactiveSyncOnJoin` set and `ReplicaCount` greater than 1; the default without the flag stays upstream's lazy repair.
- `membership-change-event` on `cluster.events`: the coordinator's announcement of every join, departure and update, carrying `change`, `node`, `node_meta`, the sorted `members` after the change and the coordinator's `generation`. It is published before the routing table is recomputed for the change and whether or not that recomputation changes the table or is allowed by `MemberCountQuorum`, so a subscriber learns of every membership change once, from one source. The `rebalance-start-event` and `rebalance-complete-event` pair remains the convergence signal.
- `storage.Replicator`, an optional capability of a storage engine's transfer iterator, and `Fragment.Replicate`, which copies every live table of a fragment to other members without dropping it, one table per hold of the fragment lock, sent with the lock released. The kvstore engine implements it. The proactive primary-to-backup push and the new re-replication use it; before, a fragment spanning several storage tables had only its first table pushed to the backups.
- The routing table push carries a table sequence, sent as an extra argument of `UPDATEROUTING` that members of the previous version ignore. It lets a member tell a new epoch under a table it already holds, see the sequence fix below.

### Changed

- **BREAKING:** `node-join-event` and `node-left-event` are delivered to the publishing member's own subscribers only. They are each member's local observation of a membership change; relaying every member's copy to every member cost `members²` deliveries per change and left consumers to work out which copy came from the coordinator. Consumers that relied on receiving other members' copies must subscribe to `membership-change-event`, the authoritative announcement. During a rolling upgrade, older members keep relaying their copies and older consumers ignore the new event kind. `EnableProactiveSyncOnJoin` also gains a duty: with it set, the survivors restore a departed member's primary copies after `ReplicaRestoreDelay`, so the flag now covers re-replication after departures as well as the push on join.
- Every remote call made on behalf of a request, replica writes, replica and previous-owner reads, read repair, and deletes on previous and replica owners, runs under the request's own deadline, or under one attempt's worth of the client timeouts (`DialTimeout + WriteTimeout + ReadTimeout`) when the request carries none, and the go-redis client now honours context deadlines at the socket level (`ContextTimeoutEnabled`). Before, these calls used the service context, which has no deadline, so a peer that accepted a connection and never answered, as a departed pod on Kubernetes does, cost every request the full read timeout times the retry count, about 20 seconds. Writes, reads and fragment transfers skip an owner that memberlist has already removed instead of dialing it: a skipped replica counts as one that did not answer and the write quorum decides, and a transfer still reaches the owners after the departed one and then reports the failure, so it is retried against the next table. Deletes do not skip: a delete has no tombstone, so a copy left on a member that was only suspected would come back through a read; a delete whose replica or previous owner memberlist removed fails at once, without a dial, and succeeds once the routing table has dropped the member. `ContextTimeoutEnabled` also applies to the Go client built from `config.Client.RedisOptions()`: a request deadline now aborts the socket call and discards the connection instead of waiting for the read timeout.
- Writes and deletes hold the fragment lock only around their storage accesses. A striped per-key lock (1024 mutexes per service) serializes the operations on one key across replication, so a key's writes still reach its replicas in the order the primary applied them, while a replica that does not answer stalls the writes of that key alone rather than every read, key count and fragment move of the partition. Measured with the race detector on a two-member cluster: a read of a fragment under sync-replicated write load went from 603µs to 94µs, and parallel replicated writes to one fragment from 138µs to 49µs per write; a local read and a single-replica write are unchanged.
- A delete of a key the primary owner does not hold still deletes the copies on the replicas and previous owners. A primary owner that took a partition over after a departure holds nothing until the backup copy is restored, and a delete that stopped at the local miss let the restore bring the key back. With `ReplicaCount` 1 and no previous owner a delete of a missing key still makes no remote call.
- The expiry scanner and the LRU eviction no longer run network deletes under the fragment lock. The scanner samples under the fragment lock and deletes each expired key under the key's own lock, checking the expiry again first; the LRU policy makes room for a replicated write before the write takes its locks, through the same delete path. An eviction can therefore no longer remove from the replicas a write of the same key that is between its replication and its store. The single-replica write keeps evicting in place under the fragment lock, and under replication the limit is a target that concurrent writes can exceed by their number.
- The proactive primary-to-backup push is keyed by the table signature instead of the install generation: the replica owners are part of the table content, so a generation that advanced for the same content, after a pull or a coordinator change, no longer re-copies every partition. Its targets are the current replica owners only, never a previous replica owner that is still draining.
- The coordinator computes the routing table with one pipelined key-count round trip per member instead of one round trip per owner per partition, reads the membership from memberlist once per computation instead of once per owner per partition, and pushes to 64 members at a time instead of `NumCPU`. At 4096 partitions on three members the computation allocates 61% less, 131k allocations instead of 336k, and measures 82ms on an idle machine.

### Fixed

- A routing table push that a member rejected or could not receive was not retried before the next periodic push, one minute later under GoAkt's settings. When the coordinator dies, the oldest survivor pushes its table about 100ms after its own memberlist declares the death, and a member whose memberlist still lists the dead coordinator rejects it with `unrecognized cluster coordinator`. The stale member kept routing to the dead node, the members that did install the table could not move fragments to it, so the epoch never completed and consumers gating on `rebalance-complete-event`, such as GoAkt's `NodeLeft`, fell back to their timeout. Reproduced with the gossip of the would-be coordinator slowed: convergence took 56.6s instead of 12s. Failed pushes are now retried with exponential backoff (200ms doubling to 2s, jittered) until they land, the member leaves, a newer table supersedes them or the periodic push is due. The epoch gates on every live member the table was computed for, including those the fan-out could not reach, which install it through the retry or their own pull and ack then; before, only the members the first push reached gated it, so a completion could be announced while a member whose push was still being retried routed requests on the old table, to the dead node. A member whose coordinator left also pulls the committed table from the new coordinator when no push has landed; the committed payload is stored before the fan-out so such a pull can never return an older table. An epoch still open after three balancer intervals is logged with the members whose ack is missing. In the reproduction the survivors now converge within 400ms of memberlist confirming the death. Addresses [Tochemey/goakt#1340](https://github.com/Tochemey/goakt/issues/1340).
- A member that missed an intermediate routing table did not ack an epoch whose table content recurred. After a member left and rejoined before any data moved, the table returned to its earlier content and signature; a member that had not installed the intermediate table saw no change, kept its generation and never acked, so the epoch stayed open until the next table change. The push now carries the coordinator's table sequence, and a member advances its generation, and acks, when the sequence changed even though the signature did not.
- A fragment that arrived while a member was installing a routing table was waited for again. The install scanned the empty partitions, asked their owners over the network, and only then reconciled the sync state; a fragment delivered in between was marked received before its partition was tracked, and the partition then waited out the whole `InitialSyncEmptyPartitionTimeout` for data it already held. This affected joins and, after the fixes above sped everything else up, most rejoins. The sync state now records the marks received during an install and the reconcile skips them.
- Every departure waited out `InitialSyncEmptyPartitionTimeout` before the node-left epoch could complete. A survivor that became primary owner of a partition it had no data for counted a backup copy held by another survivor as a source, but nothing ever moved a backup copy to a new primary owner, so the wait always ran to the escape, 5s under GoAkt's settings. A partition pending as primary now awaits only previous primary owners, whose copy `primaryCopies` moves right away; the backup copy is restored by the survivors after `ReplicaRestoreDelay`, off the convergence path.
- The proactive primary-to-backup push could leave replica owners without data. It ran once per installed table, from the install callback only, and recorded the table as pushed even when a push failed or a partition's primary copy had not arrived yet, so a replica owner that had not installed the table when the push reached it, or a partition whose primary copy was moved in later, stayed empty until the next table change. The push now runs on every balancer cycle, once per partition per installed table, as soon as the partition holds data, and a failed push is retried on the next tick.
- The balancer waited a full `TriggerBalancerInterval` (15s by default) after a cycle that moved data before it acked. A cycle that moved data is now followed by another one right away, up to three per invocation, so the ack follows the last move.
- Table computation stopped at the first empty fragment of a partition's map, skipping the fragments after it in that cycle.
- A retried routing table push could replace a newer table on a member: the retry of an older table raced the fan-out of a newer one, and a member installed whichever arrived last. A push whose sequence is older than the installed one, from the same coordinator, is now answered but not installed, and a pull issued against a version a push replaced meanwhile is dropped.
- A member whose coordinator changed pulled the table the new coordinator's push had already delivered, and the pull forgot the push identity, so the next periodic push counted as a new table and re-copied every primary this member owns to its backups. The pull stops when the installed table already came from the current coordinator, and a pull that confirms the installed table keeps the sequence of the push that delivered it.
- An early ack from a member the fan-out had not reached was dropped when the epoch started, so the ack was missing once the retried push admitted the member; every buffered ack is now kept.
- Retry rounds pushed to unreachable members one at a time, each with the client's full retry chain, so ten members dropping packets made a round outlast the push interval and retry goroutines piled up. The members of a round are pushed to concurrently, every attempt, in the fan-out as well, is bounded by one attempt's worth of the client timeouts, and the deadline is checked before each attempt.
- When the coordinator could not install its own push, the committed payload kept a table no epoch tracked; the previous commit is restored on that path. The overdue-epoch watcher is no longer started for an epoch that completed at its start.
- The restore of a departed owner's primary copy was skipped whenever the new owner already held any key of the partition: it asked the owner whether it held the partition, so a single new write made the partition count as held for the whole table. The restore now tracks, per partition, the owner list each balance cycle saw and schedules a restore when an owner dropped out of it, due `ReplicaRestoreDelay` later; when due, the restore is dropped if that owner is still a cluster member, since it drained its copy rather than dying with it, and sent otherwise, without asking, as the receiver's merge is version-aware. The decision is taken when due rather than at the change because a member's memberlist can learn of a death after the coordinator's table arrives.
- A failed promotion of a survivor's sole backup copy let the balancer relocate that copy to the new replica owner in the same cycle, dropping it locally, which is the durability race the promotion was introduced to close. A backup copy of a partition this member owns as primary is never relocated.
- `Expire` replicated the entry with an empty value; the replica stored it as pushed and, on a timestamp tie, a read served the empty value. A TTL update now carries the current value to the replicas, and equal timestamps resolve in favour of the primary's copy.
- The expiry scanner addressed the DMap by the fragment's key in the partition map, `dmap.<name>`, so its remote deletes went to a DMap that does not exist and the replicas kept every expired key.
- The janitor could wipe an empty fragment while a write was between its replication and its local store, leaving the acknowledged write in a detached fragment. A fragment with a write in flight is left alone.
- A storage import that failed to merge an entry answered as if every entry had been merged, so the sender recorded the copy as delivered; the failure is now reported.

## v0.3.19 - 2026-09-02

### Fixed

- Routing table pushes no longer start a new rebalance epoch when the table is unchanged. The routing table signature, which doubles as the rebalance epoch id, was the xxhash of `msgpack.Marshal(map[uint64]*route)`, and msgpack writes map entries in Go's randomized iteration order, so an unchanged table produced a different signature on almost every encoding. Because `updateRoutingWithReason` starts a new epoch whenever the signature differs from the previous one, nearly every periodic push (`RoutingTablePushInterval`) replaced the active epoch on a stable cluster: an epoch started for a node join or a node leave that was still waiting for acks was silently dropped and never completed, members that acked it afterwards were told the ack was stale, and `cluster.events` subscribers saw a `rebalance-start-event` with reason `periodic` followed by its `rebalance-complete-event` on every push. Consumers that gate on a specific epoch, such as GoAkt's `NodeJoined` and `NodeLeft` events, only fired through their fallback timeout whenever a member could not ack within one push interval. The payload is now encoded in ascending partition id order, so identical tables yield identical bytes and the same signature on the coordinator and on every member. The wire format is still a plain msgpack map, so members running an older version keep decoding it during a rolling upgrade. Pushing an unchanged table now starts no epoch and publishes no rebalance events, and an epoch started for a membership change stays active until every live member acks it or a genuine table change supersedes it. Fixes [#40](https://github.com/Tochemey/olric/issues/40).
- The balancer acks a rebalance epoch once per installed routing table instead of once per signature value. With content-derived signatures the table can return to an earlier state, for example after a member joined and left before any data moved, and the coordinator then runs a new epoch under the same id. A member that remembered that signature as already acked skipped the ack, which left the node-left epoch open until the next table change. The routing table now exposes an install generation that advances whenever a table with a different signature is installed, including a change back to an earlier signature, and the balancer acks once per generation. The proactive primary-to-backup push (`EnableProactiveSyncOnJoin`) is keyed by the same generation, so it also runs once per installed table. Pushes of an unchanged table advance nothing and trigger no duplicate acks or pushes.
- Members no longer hold their rebalance ack for `InitialSyncEmptyPartitionTimeout` on partitions no live owner holds data for. A member could not tell an empty partition from one whose data was still in flight, so after a membership change every owned-but-empty partition delayed the ack by the full timeout: on the reporter's cluster the node-left epoch completed about 5.5s after the departure although nothing had to move. When a routing table is installed, the member now asks each other owner of its owned-but-empty partitions for their key counts, in one pipelined round trip per owner using the same length-of-partition command the coordinator already uses to prune empty owners, and only waits on partitions where some owner holds data or could not be answered for. Partitions whose wait has already elapsed are not probed again, so a stable cluster issues no extra requests. On an empty cluster the node-left epoch now completes on the survivors' next balancer tick.
- Cluster events now identify rebalance epochs unambiguously and tell subscribers which membership changes an epoch reflects. `rebalance-start-event` and `rebalance-complete-event` carry `generation`, the coordinator's install generation of the pushed table, which unlike the content-derived `epoch` never recurs on a given coordinator; `rebalance-complete-event` also carries `members`, the sorted addresses of the members the coordinator knew when it computed the converged table; and `node-join-event` and `node-left-event` carry the `generation` the publisher held when it observed the change, so on the coordinator every epoch that reflects the change carries a higher one. Generations are comparable only between events of the same `source`. A `rebalance-complete-event` published from the epoch start, when every ack had already arrived, could carry an earlier timestamp than its own `rebalance-start-event` and reach subscribers before it; the start is now stamped before the completion check, and the completion is published only after the start has been.
- The routing table no longer races its own shutdown. Cluster event publication and the balancer callbacks were started from request handlers and membership events with a bare `wg.Add(1)` and nothing gating them against the `wg.Wait()` in `RoutingTable.Shutdown`, so a routing table push or a membership event arriving as a member shut down called `Add` concurrently with `Wait`, which the race detector flags as a `sync.WaitGroup` misuse. Those spawns now go through one helper that takes a mutex around `wg.Add`, and `Shutdown` sets a `closed` flag under the same mutex before waiting, so work arriving after shutdown has begun is dropped, which is safe because the node is leaving. The temporary diagnostic logging of routing table pushes, left from an earlier investigation, is removed.
- Cluster events reach local subscribers first and never wait on a remote member. The pubsub fan-out served local subscribers only when its member loop reached the local member and stopped at the first remote failure, so a member that was still starting, which rejects or holds requests until it is operable, could delay or lose an event for every subscriber including the local ones; `node-join-event` publishes failing with `failed to find enough peers to create quorum` during a join were this. Local subscribers are now served first, every remote member is attempted, and the first failure is reported after the last attempt. The internal publish and the key count probe used while installing a routing table are served regardless of the node's operability precondition, as the routing table push already was: neither touches user data, and both must work on a node that is not operable yet.

## v0.3.18 - 2026-07-24

### Fixed

- `RoutingTable.Start()` no longer waits on member-count quorum passively. When `MemberCountQuorum` is greater than 1 and this node bootstraps alone (its only configured peer, or the `ServiceDiscovery` backend's result, was unresolvable at `Join()` time), the quorum gate relied solely on memberlist gossip surfacing a peer, and could block for the full one-hour timeout — or forever, in practice, if no other node ever dialed in first — even though the peer became resolvable moments later. The rejoin loop, which re-resolves peers and dials them every `RejoinInterval`, is the mechanism that recovers from exactly this state, but it was started *after* the gate it needed to unblock, so it could never help during a cold start. It now starts before the gate, so a node leaves the gate as soon as a peer becomes reachable through gossip, static `Peers`, or `ServiceDiscovery`, instead of only waiting to be found. The loop remains a no-op while quorum is satisfied and is still only started when `MemberCountQuorum` is greater than 1, so the default single-node case issues no extra `Join()` calls and is otherwise unchanged.
- `DMap.Delete(ctx, keys...)` no longer silently drops keys owned by remote partition owners past the first one. `deleteKeys` groups the requested keys by partition owner, then looped over that map to delete each group; the remote-owner branch returned unconditionally after handling the first remote owner (on both success and error), so any additional remote owners in the map were never processed and no error was returned. On a multi-node cluster, a multi-key delete spanning more than one remote owner beyond the first left the keys on every owner after that one untouched. The fan-out now uses `errgroup`, matching the pattern already used by `deleteBackupOnCluster`: every owner, local and remote, is processed, and the first error (if any) is returned only after all owners have been attempted; the returned count reflects the keys actually processed across every owner.

## v0.3.15 - 2026-07-13

### Fixed

- Fixed a `sync.WaitGroup` misuse in the dmap service where cluster-event publication and async backup writes called `wg.Add(1)` from untracked goroutines (request handlers, the balancer) with no gate against the concurrent `wg.Wait()` in `Service.Shutdown`. A fragment push or backup write arriving as a member shut down (common during relocation and backup promotion) could call `Add` concurrently with `Wait`, which the race detector flags and which can, outside `-race` builds, panic with a `WaitGroup` counter misuse. All such spawns now route through a single `spawn` helper that takes a mutex around `wg.Add`, and `Shutdown` sets a `closed` flag under the same mutex before `wg.Wait()`, so `Add` can never run concurrently with `Wait`. Work dropped once shutdown has begun is safe because the node is leaving. Fixes [#24](https://github.com/Tochemey/olric/issues/24).
- `ClusterClient` operations (`Get`, `Put`, and so on) no longer fail with a raw `redis: client is closed` error during a member failover. When a node leaves, its connection pool is closed while an in-flight request may still hold the go-redis client, so that command now surfaces as the retryable `ErrConnRefused` sentinel, like a refused dial, so callers refresh metadata and retry against the promoted owner instead of getting a hard error. This removes a flake in `TestIntegration_Kill_Nodes_During_Operation`.
- Embedded `DMap.Scan` no longer stalls for minutes after a member crashes (`kill -9`, pod crash). The scan path now filters partition owners against live memberlist membership before dialing them, skipping any owner that memberlist has confirmed removed (not merely suspected, so a live member that is briefly flapping is never skipped mid-scan). Previously, a scan touching a partition still owned by the dead member in the iterator's routing-table snapshot kept dialing the dead address until repair converged. On Kubernetes a deleted pod IP drops packets, so every attempt waited out the full dial timeout, and the resulting error aborted the whole scan. The dead owner's data is served by the promoted replica, so skipping it is safe and bounds crash-recovery scans by failure detection plus one scan instead of the routing-table repair window. Fixes [#22](https://github.com/Tochemey/olric/issues/22).

## v0.3.11 - 2026-07-04

### Added

- New `ErrNotJoinedYet` sentinel error, returned by operations that depend on cluster membership when the local node has not completed its cluster join yet.

### Changed

- **BREAKING:** `Config.Validate()` now rejects LRU eviction configurations whose per-partition budget is too small for the storage engine to honor, closing a memory footgun where a modest `MaxInuse` could let allocated memory grow several times past the configured limit. When `EvictionPolicy` is `LRU`, the validation enforces two invariants:
  - `MaxInuse / PartitionCount >= tableSize` — otherwise each partition's in-use cap is smaller than a single storage table, so eviction churns tables into garbage faster than compaction can reclaim them and allocated memory grows far beyond `MaxInuse`.
  - `MaxKeys >= PartitionCount` — otherwise the per-partition key budget rounds down to zero and the cache evicts on every write.

  Both checks apply to the global `DMaps` configuration and to every entry in `DMaps.Custom`. A deployment that previously started with such a configuration (while silently over-allocating memory) will now fail at startup. To resolve the error, increase `MaxInuse`/`MaxKeys`, reduce `PartitionCount`, or lower the storage engine `tableSize`.

### Fixed

- `EmbeddedClient.NewPubSub()` without a `ToAddress` option now reliably targets the local node instead of picking a connection from the node's internal pool. The pool is populated lazily as a side effect of intra-cluster traffic, so on a freshly joined member it was usually still empty and the call failed intermittently with a confusing `no available client found` error; even when it succeeded, the PubSub client was silently pinned to an arbitrary cluster member whose departure would break it. Targeting the local node is always correct because a `PUBLISH` received by any member is relayed to the whole cluster. This prevents the startup flakiness entirely: once the `Started` callback fires, `NewPubSub()` is guaranteed to succeed. An explicit non-blank `ToAddress` still takes precedence, blank or whitespace-only addresses fall back to the local node instead of failing, and calling before the node has joined the cluster fails fast with `ErrNotJoinedYet` instead of racing on cluster state or returning a misleading error. `ClusterClient.NewPubSub()` behavior is unchanged.
